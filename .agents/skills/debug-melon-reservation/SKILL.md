# 멜론 예매 요청의 관찰 기록

기록 기준일은 2026-11-02입니다. 인증 실패를 진단하거나 변경 범위를 판단할 때 아래 기록을 참고하세요. 사용자 제공 자료, 로컬 재현 결과, 사용자 결정을 구분해 해석하세요.

## 1. 사용자에게서 보고된 인증 오류

- 사용자가 제공한 실행 로그에는 `reservation failed (): 인증예매를 완료해주세요.`라는 오류가 있었습니다.
- 로그에 출력된 결과 코드는 비어 있었습니다. 원본 오류 JSON을 확보한 것은 아니므로, 서버의 `result`가 누락되었는지, `null`이었는지, 빈 문자열이었는지는 구별할 수 없습니다.
- 이 오류 문구만으로 캡챠 만료가 원인이라고 단정하지 마세요.

## 2. 사용자 제공 성공 응답의 필드 형태

- 성공 응답 예시의 `encryptedSeatIds`는 문자열이었고, `interlockTid`는 문자열 `"0"`이었습니다.
- `staticDomain`, `httpsDomain`, `httpDomain`, `volumeTypeCode`는 `null`이었습니다.
- 이는 사용자가 제공한 한 응답의 관찰값입니다. 전체 API 스키마나 모든 응답의 필수 필드로 확대 해석하지 마세요.

## 3. 실제 설정에서 확인한 이중 인코딩 사례

- 실제 실행 코드의 요청을 전송 전에 가로채 확인했을 때, `.env`의 `CHKCAPT`에 이미 `%2F`가 들어 있었고 요청에는 `%252F`로 들어갔습니다.
- 당시 쿠키 네 개와 나머지 폼 필드 37개는 사용자가 제공한 cURL과 일치했습니다. `chkcapt`를 한 번 URL 디코딩하면 기준값과 일치하는 것도 확인했습니다.
- 해당 설정값을 원본 값으로 수정한 뒤에는 메서드, URL, cURL에서 명시한 헤더, 쿠키 네 개, 폼 값 38개가 모두 일치했습니다.
- 이 비교는 파싱한 요청값에 대한 것입니다. 폼 직렬화 순서, HTTP 클라이언트가 자동으로 붙이는 헤더, 전송 프로토콜까지 동일하다고 검증한 것은 아닙니다.

## 4. 자동 검증의 범위

- 이 작업의 자동 검증은 실제 실행 코드의 요청 가로채기, 모의 응답, 로컬 HTTP 서버로 수행했습니다.
- 모의 요청 및 출력 검증용 테스트는 임시 공간에 두고 Go의 `-overlay`로 연결했습니다. 저장소에 회귀 테스트 파일을 추가한 것은 아닙니다. 후속 검증에서 이전 임시 파일이 남아 있다고 가정하지 마세요.
- 이중 인코딩 수정 후 실제 멜론 서버로 재호출하지 않았으므로, 인증 오류가 해소되었거나 실제 예매가 성공했다고 확인한 것은 아닙니다.

## 5. 당시 사용자가 선택한 리뷰 범위

- 리뷰에서 제안한 HTTP 오류 응답의 JSON 보존과 자동 리다이렉트 비활성화에 대해, 사용자는 필수 수정인지 확인한 뒤 `넘어간다`고 결정했습니다. 당시에는 두 동작을 변경하지 않기로 했습니다.
- 이 결정을 무기한 수정 금지로 해석하지 마세요. 새로운 요구사항이나 실제 영향이 확인되면 해당 작업 범위에서 재검토하되, 과거 지적만으로 두 항목을 다시 필수 수정 사항으로 취급하지 마세요.
