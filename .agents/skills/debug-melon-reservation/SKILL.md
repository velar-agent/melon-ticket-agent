# 멜론 예매 요청의 관찰 기록

기록 기준일은 2026-11-02입니다. 인증 실패를 진단하거나 변경 범위를 판단할 때 아래 기록을 참고하세요. 사용자 제공 자료, 로컬 재현 결과, 사용자 결정을 구분해 해석하세요.

## 1. 사용자에게서 보고된 인증 오류

- 사용자가 제공한 실행 로그에는 `reservation failed (): 인증예매를 완료해주세요.`라는 오류가 있었습니다.
- 로그에 출력된 결과 코드는 비어 있었습니다. 원본 오류 JSON을 확보한 것은 아니므로, 서버의 `result`가 누락되었는지, `null`이었는지, 빈 문자열이었는지는 구별할 수 없습니다.
- 이 오류 문구만으로 캡챠 만료가 원인이라고 단정하지 마세요.

## 2. 사용자 제공 성공 응답의 필드 형태

- 성공 응답 예시의 `encryptedSeatIds`는 문자열이었고, `interlockTid`는 문자열 `"0"`이었습니다.
- `staticDomain`, `httpsDomain`, `httpDomain`, `volumeTypeCode`는 `null`이었습니다.
- 이는 사용자가 제공한 한 응답의 관찰값입니다. 전체 API 스키마나 모든 응답의 필수 필드로 확대 해석하지 마세요.

## 3. 실제 설정에서 확인한 이중 인코딩 사례

- 실제 실행 코드의 요청을 전송 전에 가로채 확인했을 때, `.env`의 `CHKCAPT`에 이미 `%2F`가 들어 있었고 요청에는 `%252F`로 들어갔습니다.
- 당시 쿠키 네 개와 나머지 폼 필드 37개는 사용자가 제공한 cURL과 일치했습니다. `chkcapt`를 한 번 URL 디코딩하면 기준값과 일치하는 것도 확인했습니다.
- 해당 설정값을 원본 값으로 수정한 뒤에는 메서드, URL, cURL에서 명시한 헤더, 쿠키 네 개, 폼 값 38개가 모두 일치했습니다.
- 이 비교는 파싱한 요청값에 대한 것입니다. 폼 직렬화 순서, HTTP 클라이언트가 자동으로 붙이는 헤더, 전송 프로토콜까지 동일하다고 검증한 것은 아닙니다.

## 4. 자동 검증의 범위

- 이 작업의 자동 검증은 실제 실행 코드의 요청 가로채기, 모의 응답, 로컬 HTTP 서버로 수행했습니다.
- 모의 요청 및 출력 검증용 테스트는 임시 공간에 두고 Go의 `-overlay`로 연결했습니다. 저장소에 회귀 테스트 파일을 추가한 것은 아닙니다. 후속 검증에서 이전 임시 파일이 남아 있다고 가정하지 마세요.
- 이중 인코딩 수정 후 실제 멜론 서버로 재호출하지 않았으므로, 인증 오류가 해소되었거나 실제 예매가 성공했다고 확인한 것은 아닙니다.

## 5. 당시 사용자가 선택한 리뷰 범위

- 리뷰에서 제안한 HTTP 오류 응답의 JSON 보존과 자동 리다이렉트 비활성화에 대해, 사용자는 필수 수정인지 확인한 뒤 `넘어간다`고 결정했습니다. 당시에는 두 동작을 변경하지 않기로 했습니다.
- 이 결정을 무기한 수정 금지로 해석하지 마세요. 새로운 요구사항이나 실제 영향이 확인되면 해당 작업 범위에서 재검토하되, 과거 지적만으로 두 항목을 다시 필수 수정 사항으로 취급하지 마세요.

## 6. 추가 관찰 사실 (이번 세션에서 재확인)

- 로그인 시간이 만료되면 서버는 `code=T9220`과 `로그인 시간이 만료되었습니다`를 보냅니다. 결과 필드는 비어 있습니다.
- 성공하면 서버는 `result=0000`을 보냅니다. 성공이라도 이전에 성공한 예매나 인증 만료를 보장하지는 않습니다.
- `MAC`과 `MLCP`는 로그인을 새로 하면 바뀌는 값입니다. 낡은 값으로 호출하면 만료 오류가 납니다.
- 브라우저가 보내는 쿠키 이름은 `PCID`입니다. `PC_PCID` 이름으로 보내면 서버가 못 알아봅니다. `PC_PCID`는 옛 이름입니다.
- 날짜와 회차 번호는 한 쌍이어야 합니다. `20261128`은 `100022`와, `20261231`은 `100036`과 같은 묶음입니다. 짝이 맞지 않으면 다른 회차로 처리될 수 있습니다.
- `CHKCAPT`는 캡챠용 일회성 값입니다. `CALLBACK`과 함께 없거나 비어 있어도 코드가 먼저 막지 않습니다. 비어 있으면 빈 값으로 보냅니다.
- 브라우저는 먼저 `ticket.melon.com`에 들어가 `PCID`를 받고, 로그인 페이지에서 `_MLBRU`와 `MRU`를 받습니다. 로그인 성공 후에는 `keyCookie`, `MAC`, `MLCP`, `MUS`를 받습니다.
- 카카오 비밀번호는 `p` 값으로 암호화해서 보냅니다. 이 방식은 HAR에서 직접 확인했습니다.
- 카카오가 `status=-451`이면 문자 인증, `status=-481`이면 캡챠 해결이 필요하다는 신호입니다. 캡챠는 자동 코드로 해결하지 않고 중단합니다.
- `_T_ANO`는 브라우저가 만드는 값이 아닙니다. Tiara 추적 응답이 서버에서 발급하는 값입니다.
- 검사 쿠키는 `__T_`와 `__T_SECURE`입니다. `__T__`로 쓰면 서버가 검사하지 않습니다.
- `loginProcs`가 경로 없는 쿠키를 보내면 세션을 찾을 때 `loginProcs` 주소 자체를 함께 봐야 합니다.

## 7. 추가 관찰 사실 (2026-11-17, Melon 클라이언트 리팩터링 세션)

- 메인 폴더의 `main.go`에는 아직 커밋되지 않았고 함수도 구현되지 않은 `receipt, err := melon.Pay(session, reservations)` 코드가 들어 있었습니다.
- 메인 폴더와 작업 워크트리에 편집기 임시 파일(`.main.go.swp`)이 남아 있고 `vim`이 `main.go`를 열어 두고 있습니다. 커밋할 때 `git add -A`를 쓰면 임시 파일이 함께 올라가므로 수정한 파일 이름만 직접 지정해야 합니다.
- 메인 폴더의 `main.go`에 미커밋 수정이 있으면 바로 머지할 수 없어 `git stash`로 잠깐 빼두었다가 머지·푸시 뒤에 되돌려야 합니다. 머지 뒤에는 `session` 변수가 없어지므로, 되돌린 `melon.Pay(session, reservations)` 줄 때문에 현재 메인 폴더 워킹트리는 그대로 빌드되지 않습니다.
- 이 저장소는 `velar-agent` 계정과 `gh` 인증 도우미를 써서 푸시하도록 설정되어 있습니다. 하지만 `gh`의 현재 활성 계정이 다른 계정(`xiote-dev`)이면 인증 도우미가 토큰을 내주지 않아 `git push`가 비밀번호 입력 대기에서 멈춥니다.
- 원격에 푸시하려면 먼저 `gh auth switch --hostname github.com --user velar-agent`로 활성 계정을 바꾼 뒤 푸시해야 합니다. 푸시가 끝나면 기존 환경이 바뀌지 않도록 `xiote-dev`로 다시 돌려놓아야 합니다.
- `Melon` 생성자와 메서드 변경은 `go vet`, `go build`, 가짜 HTTP 서버를 쓰는 단위 테스트로만 확인했습니다. 실제 카카오 로그인이나 멜론 예매 서버까지는 실행해 보지 않았습니다.
- `agy` 코드리뷰에서 나온 `New` 성공 단위 테스트 추가와 기능 제안(`Login`/`Session` 숨기기, 자동 재로그인, 인터페이스 분리, `context.Context` 지원, 로그인 상태 확인 메서드)은 기존 로그인 테스트 커버리지와 요청 범위 제한을 이유로 이번 변경에 반영하지 않기로 했습니다.
- `agy` 명령에 `Gemini 3.8 Flash (High)` 모델을 지정해 비대화형 코드리뷰를 돌리면 결과가 나올 때까지 한 번에 약 2분 40초~3분 정도 걸립니다.
- 이 저장소는 메인 폴더 외에 에이전트별 작업 워크트리(`8519`, `f61a77e9`, `33e4322f`)가 여러 개 함께 남아 있습니다. 이번 세션의 `33e4322f` 워크트리도 머지·푸시 뒤 삭제하지 않고 남겨 두었습니다.
